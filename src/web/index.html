Set it up oncea GitHub App is the whole of it — every token a box gets is minted from this one key
One credential, and skein derives the rest: a write token scoped to a box's own repository, and a read-only one covering everything you installed the App on — both minted per box, valid an hour, renewed while the box runs. Nothing below is needed on this path.
Without a GitHub Appstore tokens yourself — this is the path that asks for more than one
For a fleet where installing an App is not an option. It costs what the App path avoids: one token per repository you want boxes to push to, kept in step by hand as they expire. Reads then come from public access, or from a second token below.
Repository tokensone fine-grained PAT per repo, and one repo per PAT
Each covers exactly one repository, and that is the whole security argument: a token covering three would hand all three to whichever box receives it, because the helper that chooses between them runs inside the box as the agent's own uid. A helper routes; it cannot contain. A repo's token can also be set on its own card under Repositories.
storing the same repo again replaces its token — that is how you rotate one
Use this account's gh tokenthe third path — no App, no per-repo tokens, and no narrowing either
The one credential that is not scoped to anything: whatever gh auth token returns, which is your whole GitHub account, copied into the sandbox-wide secret and reachable by every box. It exists because it needs no setup — nothing to create, install or rotate per repo — and that is the entire trade. Prefer it only for a fleet whose repos you would hand any box wholesale.

Off until you pick it. It used to be on by default, which made the broadest of the three the one nobody chose — and on Linux gh keeps its token in the login keyring, so startup asked to unlock it every time.
